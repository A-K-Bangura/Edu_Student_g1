# Decisions Log — `edu-student`

*Records why a non-obvious choice was made, so a future contributor doesn't "fix" it back into a problem. Add an entry whenever a decision is made that isn't self-evident from the code — architecture, library choice, a deliberate deviation from the obvious approach, a tradeoff accepted knowingly. This log did not exist before this audit; the entries below are decisions inferred from evidence already in the repo, not new decisions made today.*

Format: **Date — Decision.** Why. Evidence.

**Pre-existing — Tailwind v4, CSS-first config, no `tailwind.config.js`.**
Why (inferred): Tailwind v4's `@tailwindcss/vite` plugin supports theme configuration directly in CSS via `@theme`, removing the need for a JS config file. The custom color scale (azure/amber/rose/aquamarine/blue-violet) lives in `src/index.css`.
Evidence: `vite.config.ts` imports `@tailwindcss/vite`; no `tailwind.config.*` exists anywhere in the repo; `src/index.css` defines the full token set.

**Pre-existing — API base URL resolved at runtime, with a same-origin fallback in production.**
Why: the backend is served over plain HTTP (see `vercel.json`'s rewrite target, a raw IP), and a production site served over HTTPS cannot call an HTTP API directly (browsers block it as mixed content). Rather than requiring a baked-in HTTPS API URL at build time, `src/config/env.ts` detects the HTTP/HTTPS mismatch at runtime and falls back to a same-origin `/api/v1` path, which `vercel.json` then rewrites server-side to the real (HTTP) backend.
Evidence: commit `feecbd6 Avoid mixed-content by resolving API_URL at runtime`; inline comment block at the top of `src/config/env.ts`; `vercel.json`'s `/api/v1/:path*` rewrite.

**Pre-existing — No path aliases; all imports are relative.**
Why: unclear from the repo alone — no comment or commit explains it either way. Noting as observed fact, not an endorsed decision. Introducing aliases now would be a real (if small) architectural change — get sign-off first per CLAUDE.md §7 before doing so.
Evidence: `tsconfig.app.json` has no `baseUrl`/`paths`; every import across `src/` uses relative paths (`../services/...`, `../../types/...`).

**2026-09-28 — `npm run type-check` fixed to actually check files.**
Why: the script was `tsc --noEmit`, which resolves against the root `tsconfig.json`. That file has `"files": []` and only `references` (a TS project-references setup) — running plain `tsc --noEmit` against it checks nothing and always exits 0, regardless of real type errors elsewhere in `src/`. Changed to `tsc -b --noEmit`, which correctly builds through the project references. Verified by deliberately introducing a type error and confirming the script caught it, then reverting.
Evidence: `package.json`'s `type-check` script; `tsconfig.json`'s `files: []` + `references`; this session's verification (see chat history / `docs/KNOWN_ISSUES.md` #1).

**2026-09-29 — New public `Landing.tsx` page at `/` for guests, rather than reusing Courses/Feed as the homepage or leaving `/` as a login redirect.**
Why: the backend added guest (no-account) browsing for Courses/Course Detail/Feed (`docs/STUDENT_FRONTEND_API_CHANGES.md` "Round 3"). Before this, `/` and any unmatched route hard-redirected straight to `/auth/login` — there was no unauthenticated experience at all. Reusing a bare course list as the entry point would skip the value-prop pitch that makes guest browsing worth having (the whole point is to hook visitors before requiring signup); leaving `/` untouched would make guest browsing invisible from the app's own navigation. Presented as an explicit tradeoff to the owner (see chat history) and this was the chosen option. `Courses.tsx`/`CourseDetail.tsx`/`Feed.tsx` are otherwise untouched content-wise — just unwrapped from `ProtectedRoute` and given a small guest guard on account-scoped actions (enroll/like/comment/share redirect to `/auth/signup` via `src/utils/guestGuard.ts` instead of hitting a 401).
Evidence: `src/pages/Landing.tsx`; `src/App.tsx`'s `/` and `*` routes; `src/utils/guestGuard.ts`; `src/components/common/GuestBanner.tsx`.

**2026-09-29 — Auth-required background calls in `Feed.tsx` (`feed-time`, `endFeedSession`, dashboard XP) are gated behind `isAuthenticated()` rather than left to fail and be caught.**
Why: `GET /student/feed/remaining` and `POST /student/feed/session/end` still require a Student account even though the feed itself doesn't (per the same Round 3 doc). Left unconditional, these would 401 for every guest page-load/unmount, and the existing axios response interceptor force-redirects to `/auth/login` on **any** 401 from any page — so a guest browsing the feed would get silently bounced to login by a background call they never triggered. Gating them (`enabled: isAuthenticated()`, and skipping the unmount cleanup call) avoids the calls entirely rather than relying on interceptor behavior to paper over them. As defense in depth, the interceptor itself was also changed to only redirect on 401 when a token actually existed (`src/services/api.ts`) — a guest who was never logged in has no session to expire and shouldn't be redirected by a missed edge case.
Evidence: `src/pages/Feed.tsx`'s `feed-time`/`dashboard` queries and the unmount cleanup effect; `src/services/api.ts`'s response interceptor.

**2026-09-29 — Offline write queueing wired at the `updateCourseProgress` service level, not at `submitQuiz`/`completeLesson`.**
Why: investigating "add offline support for quiz submission and lesson completion" (the owner's scoping) turned up that `services/quiz.ts::submitQuiz` and `services/lessons.ts::completeLesson` are both dead code — `CoursePlayer.tsx` grades quizzes locally and marks both lessons and quizzes complete through a single shared endpoint, `services/courses.ts::updateCourseProgress` (`POST /student/courses/{course}/progress`, `{lesson_id|quiz_id, completed}`). Wiring the queue into the dead functions would have shipped a feature nobody's code path exercises. Instead: `updateCourseProgress` checks `isOnline()`/catches network errors, calls `utils/db.ts::queueOfflineAction`, and throws a new `OfflineQueuedError` instead of returning normally when queued. `CoursePlayer.tsx` catches that specifically (in the quiz-progress-sync path and the lesson-completion path) and shows a "Saved Offline" state — a new `queued` status alongside the existing submitting/success/error ones — rather than a generic error, and treats it the same as `success` for unlocking progress to the next screen (the whole point of offline support is letting the student keep going). `services/sync.ts` also picked up two related fixes while touching this: it now actually increments and persists `retryCount` on failure (previously always stayed `0`, so a permanently-failing action would retry forever instead of being dropped after 3 tries), and `initSync`/`syncOfflineActions` take an `onActionSynced` callback so `OfflineIndicator.tsx` can invalidate the whole React Query cache once something syncs (simplest correct option — sync events are rare, so a broad invalidate over a hand-maintained list of affected query keys was judged not worth the complexity). Course enrollment and feed actions were explicitly scoped out by the owner and are not queued.
Evidence: `src/services/courses.ts::updateCourseProgress`; `src/utils/db.ts` (`OfflineQueuedError`, `isNetworkError`, `queueOfflineAction`, `bumpOfflineActionRetryCount`); `src/services/sync.ts`; `src/pages/CoursePlayer.tsx` (`progressStatus`/`lessonCompletionStatus` `"queued"` branches, the offline completion modal); `src/components/common/OfflineIndicator.tsx`. Live-verified end to end (queue → IndexedDB → reconnect → real backend POST → queue drained) — see `docs/PROJECT_STATE.md`.

**2026-09-30 — Paid-course checkout redirect uses `window.location.href`, not React Router `navigate`; polling lives directly in `CourseDetail.tsx`; unenroll UI deliberately not built.**
Why: the backend shipped Round 4 (Monime one-time-payment checkout for paid courses — `docs/STUDENT_FRONTEND_API_CHANGES.md`/`docs/STUDENT_API_PAYLOADS.md` §12/§14/§16/§16a/§18). `POST .../enroll` on a paid course now returns `{requires_payment: true, checkout_url}` instead of enrolling immediately, and the student must be sent to Monime's hosted page — a real cross-origin navigation away from the SPA, so `window.location.href` was used instead of `navigate()` (React Router can't and shouldn't try to route to an external origin). After paying, Monime returns the browser through the backend to `{STUDENT_PORTAL_URL}/courses/{slug}?payment=success|processing|cancelled|expired` — **plural** `/courses`, unlike this app's existing **singular** `/course/:courseId` detail route — so a second, identical route (`/courses/:courseId` → the same `CourseDetailPage`) was added as an alias rather than renaming the existing route or asking the backend to special-case its return path. The `?payment=` value is read once on mount into local state (so the banner survives the URL being stripped) and is only ever a display hint, never trusted as proof of payment — `processing` triggers polling `GET .../enrollment-status` (which independently re-checks with Monime) every 3s until `state === "enrolled"`, consistent with the docs' explicit warning that a forged query string changes nothing server-side. This polling/banner logic lives inline in `CourseDetail.tsx` rather than a new hook or shared component — it's a single call site and the plan was to keep this change's footprint small. Separately, `unenrollFromCourse` (`src/services/courses.ts`) was left as pre-existing dead code and **not** wired to a UI button in this change — no enrolled-course screen has ever had an unenroll affordance, and Round 4 makes unenroll meaningfully more nuanced for paid courses (no refund; requires a "you won't get a refund" confirmation before calling it) — building the first unenroll UI at all is new scope beyond making paid enrollment work, so it's flagged here as a follow-up rather than added silently.
Evidence: `src/pages/CourseDetail.tsx` (`handleEnroll`, the `paymentBanner` state/effects, the `enrollment-status` polling query); `src/App.tsx`'s `/courses/:courseId` route; `src/services/courses.ts` (`enrollInCourse`'s `EnrollResult` union, `getEnrollmentStatus`); manually verified end-to-end against the real backend and a real Monime checkout page in this session (redirect fired correctly, showed the right price; payment intentionally not completed since that would be a real financial transaction).

Why: the backend shipped Round 5 (Vybe Coins — a second reward currency, separate from XP, earned once per student per paid-course completion and exchangeable for Leones via Mobile Money; `docs/STUDENT_FRONTEND_API_CHANGES.md`/`docs/STUDENT_API_PAYLOADS.md` §66-69). Live-verified against the real backend after the fix (empty-state History/My Requests tabs render correctly, no console errors).
Evidence: `src/pages/Dashboard.tsx`/`src/pages/Profile.tsx` (new stat cards/tiles), `src/pages/CoursePlayer.tsx` (`coinsAwarded` on `lessonCompletion`, the gold banner), `src/services/coins.ts` (`getCoinTransactions`/`getExchanges`), `src/types/coins.ts` (`PageMeta`, `CoinTransactionList`, `ExchangeList`).

**2026-10-01 — Landing page rebuilt per the design guide; brand fonts wired globally; landing links exempted from the global `a` rule.**
Why: the owner supplied `docs/designs/univybe_landing_page_implementation_design_guide.md`, the two display fonts, and mascot/floating art. Non-obvious choices: (1) **Fonts** — Super Greatly (`font-title`) only for the six section titles per the owner; Bangers (`font-accent`) for the hero and final-CTA headlines and eyebrow labels. TTFs are used as-is (no Python/woff2 tooling on the machine; converting needs a tool or dependency, so it's deferred) with `font-display: swap`. (2) **`a:not(.landing-root a)`** — `index.css` declares `a { color; font-weight }` *unlayered*, and unlayered CSS beats Tailwind v4's layered utilities, so every `text-*`/`font-*` class on a landing link was being overridden (CTAs rendered purple at weight 500). Rather than move the global rule into `@layer base` (which would silently change link colours on every other page), the rule now skips anything inside `.landing-root`. (3) **Always light, no `PageShell`** — the landing page is a brand surface whose multicolour wordmark needs a light hero; it ignores the in-app dark-mode toggle. (4) **CTAs to unbuilt pages go to sign-up** — there are no practical-sessions, resources or opportunities routes in `App.tsx`; the guide forbids inventing routes, so those three CTAs keep their designed labels but link to `/auth/signup` (the app's existing guest strategy; see `utils/guestGuard.ts`). Constants live in `landingSections.ts` — repoint them when the pages exist. (5) **Light-tone body copy is bold** — white on `#3A86FF`/`#FF006E` is ~3.5–3.8:1; bold ≥18.66px counts as WCAG "large text" (3:1). Palette left as specified. (6) **Cards (lesson, campus pass, project board, resources, opportunities…) are CSS/SVG, not images** — crisp, zero image weight, and the guide prefers existing assets + GSAP over generation. (7) **Only 3 mascots + 1 coin were generated** (Higgsfield `gpt_image_2_5`, ~2 credits) for the sections with no suitable existing pose (practical, coins, opportunities); existing `Hi`, `vybe_hat`, `learning`, `vybe_smart` cover the rest. (8) **PWA runtime cache for `.webp`/fonts** instead of widening the precache glob (which would force every first-time visitor to download all landing art during SW install).
Evidence: `src/pages/Landing.tsx`, `src/components/landing/*`, `src/hooks/useFeatureSectionAnimation.ts`, `src/index.css` (`@font-face`, `font-title`/`font-accent`, `a:not(.landing-root a)`), `scripts/optimize-assets.mjs` (named `optimize-landing-assets.mjs` when this entry was written), `vite.config.ts` (`landing-assets` rule), `src/pages/Landing.test.tsx`.

**2026-10-01 — App-chrome logos moved to a separate `brand` WebP set in a generalized `optimize-assets.mjs`; precache widened for exactly those files.**
Why: `TopNav` and the three auth pages bundled ~3.3 MB of 1024² / 1655×639 PNGs (Workbox precache 8.9 MB) to draw logos at 60–160 CSS px. Non-obvious choices: (1) **Separate `src/assets/brand/` folder + index, one shared script** (renamed from `optimize-landing-assets.mjs`; `assets:landing` still works) — the script wipes stale `*.webp` per output folder and the landing index is a string-keyed record for optional art, so mixing app chrome into `landing/` would have coupled two unrelated asset sets and polluted `landingImages`. The brand index uses named exports instead, so a typo fails `tsc` rather than rendering `src={undefined}`. (2) **`trim: false`** — unlike landing art, the logo canvases (icon glyph is 509×644 inside 1024²; wordmark has margins) are laid into fixed boxes (`w-40 h-40`, `w-15 h-15`, `h-8 w-auto`); trimming would stretch the icon and change the wordmark's size. Verified the swap is layout-identical (same element boxes at every viewport). (3) **Icon at 160 *and* 320 px, not just 160** — the auth pages render the icon at 160 CSS px (the brief assumed ~60), and the glyph only fills ~half the canvas, so 2× needs a 320 px source; TopNav (60 CSS px) uses 160. Wordmark 420 px wide for both nav sizes. (4) **`alphaQuality: 95`** for logos — the edge is all alpha (RGB is one flat colour plus a faint halo); default 85 is fine for photos/mascots but cheap to raise here (6 files, ~60 KB). (5) **`assets/brand-*.webp` added to the Workbox precache glob** — the PNGs were precached, so dropping them would have meant a first-time offline visitor saw a broken logo until the runtime cache warmed. Hence the `brand-` filename prefix (Vite keeps the source basename in hashed output). Result: precache 8,925.6 → 5,685.0 KiB. (6) **`public/*.png` left alone** per the owner (see `docs/KNOWN_ISSUES.md` #30: ~4.3 MB of it is still precached and unreferenced).
Evidence: `scripts/optimize-assets.mjs`, `src/assets/brand/index.ts` (generated), `src/components/layout/TopNav.tsx`, `src/pages/Auth/{Login,Signup,VerifyOtp}.tsx`, `vite.config.ts` (`globPatterns`), `package.json` (`assets`, `assets:landing`, `assets:brand`), build output (`precache 74 entries (5685.00 KiB)`).

**2026-10-03 — Roadmaps, course discovery upgrade, fallback covers, and mascots on the auth/onboarding screens.**
Why / what, in order of how likely each is to be "fixed" back into a problem:
(1) **No "join roadmap" and nothing locked** — the backend contract is explicit (`docs/STUDENT_API_PAYLOADS.md` "Roadmaps"): participation is automatic from taking *any* course, order is guidance. Every journey node is a plain link whatever its neighbours' state; the "jump to current course" control (first a header "Continue/Explore roadmap" button, now a small button in the title bar's details, see 2026-10-05) only scrolls/jumps (to `current_course.page` + the current node) and never enrols. A test asserts no lock/join UI.
(2) **Stage size 8, `page=current`, then the lighter `/courses` endpoint** — short roadmaps fit on one stage; the first request lands a returning student on the stage with their current course; flipping stages doesn't re-fetch progress (paging never changes it). `current_course.page` is only valid at the `per_page` that was requested, which is why the size is a single constant (`STAGE_SIZE`) shared by both queries.
(3) **Stage colours are a pure hash of `slug + page`** that skips the previous page's colour — varied-looking but identical every visit, as the guide requires. Fallback course covers use the same idea (hash of slug/uuid) and are pure SVG/CSS: per CLAUDE.md §23 nothing is generated per course.
(4) **Node = `<Link>`; hover popover vs tap sheet is decided by `(hover: hover) and (pointer: fine)`**, not by screen width, so a touch laptop or a small desktop window each get the right behaviour. On touch the click is intercepted to open the sheet; for mouse/keyboard it navigates, and Escape dismisses the preview without moving focus.

Cleared on success, on explicit logout (all accounts — shared devices) and when the server says onboarding is done; **kept on session expiry**, because the whole point is resuming after one. A draft is advisory: server profile and live lists win.
- *Revalidate, never substitute.* A restored university/faculty/department that isn't in the current lists (or whose parent chain doesn't match, which the nested endpoints enforce) is cleared with a visible notice and the student re-chooses; the app never auto-selects a "closest" one, and steps 3–4 stay blocked until every regular-level selection is confirmed against the live lists. Faculty/department requests aren't even sent until their parent is confirmed.
- *Session recovery goes through email re-verification, not login,* for a student who never finished onboarding (no usable password until then — `KNOWN_ISSUES` #48). The 401 handler routes pending sessions to `/auth/signup?reason=session-expired` with the email pre-filled; full sessions still go to `/auth/login`.
- *Exclusive sessions.* Storing a pending session clears the full one and vice-versa. Otherwise a previous account's `auth_token`/`user` could satisfy the route guard for a different, newly verified account.
- *WhatsApp is a link, not an action.* A real `<a href="https://wa.me/…" target="_blank" rel="noopener noreferrer">` rather than `window.open`: no popup blocking, works with long-press/copy, and nothing happens in the app besides noting the request. The UI says "nothing has been sent yet" and only says an institution is available once the API returns it. The message contains institution names only; student-typed text is whitespace-flattened and capped (it can't forge extra template lines). Support number is `VITE_SUPPORT_WHATSAPP_NUMBER`; no number is invented, an unset/invalid one shows an "unavailable" message instead of a dead link.
- *Focus revalidation, not polling.* The three lookup queries opt in to `refetchOnWindowFocus` (app default is off) with a 30 s `staleTime`; a manual "Refresh list" / "I've contacted support — check again" invalidates the same keys other pages share.
- *Level change keeps selections within the same kind* (100→200 keeps university/faculty/department; university-level ↔ UnderGrad/graduate still resets). Previously any level change wiped them, which defeated "preserve valid selections".
- *Skipped:* a searchable selector (new UI pattern), backend changes, and any new token storage.
