### Onboarding resume and institution support (2026-10-26)

Fixed in this round (details in `docs/ARCHITECTURE.md` §16): the onboarding draft restore was effectively broken (the autosave effect overwrote the stored draft with the blank form before the load effect read it); the draft was unscoped, unversioned, didn't store the step, and **wrote the password and confirmation to localStorage in plaintext**; a pending (verified-not-onboarded) student reopening `/` landed on the guest landing page; a 401 on a pending token was ignored (stuck on onboarding); lookups had no failure / empty / retry / refresh state; a stale `auth_token` from a previous account could coexist with a new pending session.

47. **Lookup endpoints may be paginated — unverified.** `docs/STUDENT_API_PAYLOADS.md` calls `GET /universities`, `…/faculties`, `…/departments`, `/organizations` "paginated", but the frontend has always read `data` as a bare array. `services/onboarding.ts` now tolerates either shape but still requests only the first page. If the backend really paginates (default page size), later entries would be missing from the selectors and "Can't find your …?" would show for institutions that exist. The local backend wasn't answering during this round, so this couldn't be checked live. **Backend to confirm** (bare list, or a `per_page`/`all` option).
48. **Incomplete accounts can't use password login (backend design).** `verify-otp` creates the student with a random unusable password; `complete-onboarding` is where the real one is set. So "session expired → login → resume" for a student who never finished onboarding is necessarily "session expired → verify email code again → resume" (the draft is kept and found again because it is keyed by the same user id). If the backend should instead keep such sessions alive longer or offer a resume token, that's a backend change. Also: the documented `verify-otp` response has no `requires_onboarding` field; the frontend derives it from the returned user (no names/level) and treats the flag as an additional signal only.
49. **`VITE_SUPPORT_WHATSAPP_NUMBER` must be set for the support flow to produce a link.** There was no existing support/admin WhatsApp number anywhere in the repo, docs or API. Until the owner sets it (build-time, see `.env.example`) the dialog shows "WhatsApp support isn't available right now". Deliberately no placeholder number.
50. **Selectors are native `<select>`s with no search box.** The "no matches" help still appears when a list is empty, but there is no in-selector search; very long department lists would benefit from a searchable select. Not built (out of scope; would be a new UI pattern).
51. **`student_id` doc/form mismatch — fixed 2026-10-31 (see below); `organization_id` still open.** The docs say both are required (`student_id` for levels 100–500, `organization_id` for UnderGrad/graduate) but the form treated both as optional. `organization_id` was deliberately left as-is — the code already has an explicit "organization is optional" comment/design (no join-gate, no lock, same pattern used across roadmaps/courses for this field), and changing it without confirming against the owner/backend risked breaking a working flow for organization-affiliated students over an untested assumption. Flagging it again here since the same class of bug (docs say required, form doesn't enforce it) could be live for this field too — **backend/owner to confirm** before touching it.
52. **Not verified against the real backend.** Unit tests mock the services and a real browser was driven against a throwaway fake API (resume at `/`, dialog, link, focus revalidation, failure/Retry, mobile width, expired-session notice). The real `complete-onboarding` / `profile` round trip for a pending token has not been exercised in this round.

1. **MCQ/true-false quizzes always graded as wrong, regardless of the answer picked.** Root cause: `docs/STUDENT_API_PAYLOADS.md` §25/26 documents `correct_answer` as an array of the literal **option text** (e.g. `["A container for storing data values"]`), but `QuizRenderer.tsx::normaliseOptions` rebuilt every option's `id` as its **stringified array index** ("0", "1", …) — a leftover assumption from before the real contract was confirmed live. A submitted index could never equal `correct_answer`'s text, so every submission failed regardless of correctness. Fixed by using the option's own text as its `id` (for `question.options`, `quiz.options`, and the `true_false` True/False fallback) so the comparison in `utils/quizValidation.ts` (itself already correct) compares text to text. Also added `"mcq"` to the `QuizType` union (`types/quiz.ts`) — the real backend sends `quiz_type: "mcq"`, not the previously-assumed `"multiple_choice"`; this didn't change behavior (`mapQuizType`'s `default` already covered it) but was a stale/misleading type. New regression coverage: `src/components/course/QuizRenderer.test.tsx` (3 tests, shaped exactly like the documented payload) — confirmed these fail against the pre-fix code and pass against the fix. Live-verified: selecting the wrong true/false answer showed "Not quite right"; selecting the right one showed "Great job! That's correct." / "Quiz Passed, Score: 100%" and unlocked the Complete button.
2. **Lesson toolbar scrolled up with the content instead of staying fixed at the bottom.** Root cause: `body { min-height: 100vh }` (plain CSS, `src/index.css`) and `PageShell`'s own `min-h-screen` wrapper both floor the page's height to the *static/large* viewport (`vh`), which on mobile can be taller than the *actually visible* viewport while the browser's address bar is showing (`dvh`). `CoursePlayer`'s own layout is a fixed `h-dvh` box that doesn't grow to fill that slack, so the leftover `vh − dvh` gap let the whole **document** scroll — dragging the header and toolbar (both inside that fixed box, not independently fixed) up and out of view together with the content, rather than only the content panel scrolling internally as intended. Fixed by switching `body`'s `min-height` and `PageShell`'s wrapper to `100dvh`/`min-h-dvh`, and added `overscroll-contain` to the lesson content panel as a second line of defense against scroll-chaining. Live-verified: with the viewport artificially shrunk and 2000px of injected content forcing a scroll, the header and toolbar stayed pixel-identical in place while only the content scrolled underneath; confirmed via `document.scrollingElement.scrollTop`/`scrollHeight` that the document itself has zero scroll room (`scrollHeight === innerHeight`).
3. **Progress bar moved below the header; color changed from blue (azure) to green.** Simple reorder + one class change in `CoursePlayer.tsx` — the bar's derivation (screen position only, not completion) is unchanged. Live-verified on both mobile and desktop widths.

`type-check`/`lint`/`build` all pass; full suite **165/165 tests**.

### Lesson completion re-submitted on every review visit — fixed (2026-10-29)

`CoursePlayer.tsx::handleCompleteLesson` unconditionally POSTed `updateCourseProgress(courseId, {lesson_id, completed: true})` on every click of the final-screen action — including when revisiting a lesson the server already has marked complete (`lessons_completed`/the outline's own `is_completed`, derived the same way as the lock state via `deriveCompletedLessonIds`). Every review or retry of an already-done lesson therefore re-submitted completion to the backend for nothing, and — depending on how idempotent the backend's XP/coin award logic is — risked re-awarding XP/coins, and would burn an offline-queue slot (`utils/db.ts`) pointlessly when offline.

Fixed: `handleCompleteLesson` now checks `completedLessonIds.has(activeLessonId)` before submitting; if already completed, it skips the network call entirely and shows a new, distinct "Lesson Already Completed" modal (course progress % pulled from the already-loaded `courseProgress` query, no fabricated XP/coins) instead of the normal celebratory one. The quiz on a lesson's last screen must still be answered correctly to unlock the action, same as before — reviewing an already-completed lesson doesn't skip that gate. (At the time this was written the per-quiz progress call was left unaffected; see the follow-up immediately below, same day, which closes that gap too.)

New regression coverage: `src/pages/CoursePlayer.test.tsx` ("already-completed lesson" — confirmed to fail against the pre-fix code). Live-verified against the real backend on an already-completed lesson: clicking "Complete Lesson" after passing its quiz produced **zero** additional requests to `/student/courses/{course}/progress` (checked via the browser's network log — only the earlier quiz-submission POST was present) and showed "Lesson Already Completed" with the real course progress (100%).

`type-check`/`lint`/`build` all pass; full suite **166/166 tests**.

### Same fix extended to per-quiz progress (2026-10-29, same day)

The owner asked for the identical treatment on quizzes: `handleQuizSubmit` also unconditionally POSTed `updateCourseProgress(courseId, {quiz_id, completed: true})` on every correct/max-attempts submission, including for a quiz the server already has marked complete (`completedQuizIds`, the same derivation the outline's quiz checkmarks use). Fixed the same way: if `completedQuizIds.has(quizId)`, skip the network call and set `progressStatus: "already_completed"` directly, which — like `"success"`/`"queued"` already did — unlocks the Next/Complete action (`isQuizNextLocked` updated accordingly) without a round trip. A new inline feedback block ("This quiz is already completed — your earlier result still counts.") replaces the "Syncing your course progress..." one for this case; the per-question correct/incorrect grading and retry mechanics in `QuizRenderer.tsx` are completely untouched — only whether the *result* gets re-POSTed changes.

New regression coverage: `src/pages/CoursePlayer.test.tsx` ("already-completed quiz" — confirmed to fail against the pre-fix code; also asserts that an independently not-yet-completed lesson in the same fixture still submits normally, proving the two skip paths are isolated from each other). Live-verified against the real backend, chained together: on a lesson whose one quiz and whose own completion were already recorded server-side, answering the quiz correctly showed the new "already completed" message and the Complete button unlocked immediately; clicking Complete then showed "Lesson Already Completed". The network log for this entire sequence showed **zero** `POST` requests — only the background `GET`/`OPTIONS` React Query traffic.

`type-check`/`lint`/`build` all pass; full suite **167/167 tests**.

### Mobile onboarding 422 at final submit — fixed (2026-10-31)

The owner reported a 422 at the end of onboarding on mobile, suspecting a missing student ID, and noted desktop worked fine once it was entered.

Root cause: a pre-existing, already-flagged gap (#51) — `docs/STUDENT_API_PAYLOADS.md`'s "Complete Onboarding" request-fields table documents `student_id` as **required for levels 100-500**, but the frontend treated it as fully optional: the input's placeholder literally said "(optional)", `utils/onboardingValidation.ts::stepFieldMessage` never checked it, and `Onboarding.tsx`'s submit mapping only included it `if (data.student_id)` — silently omitting it when blank instead of blocking submission. Any regular-level student who left the field empty got a 422 (`VALIDATION_ERROR`, `student_id` required) on the final "Complete" click, after already filling in three steps' worth of other fields. This isn't a mobile-specific code path — the same form renders everywhere — but a field labeled "(optional)" and sitting at the bottom of a longer step is far more likely to get skipped on a small screen than on desktop, matching the owner's own observation exactly (works once the student ID is entered, regardless of device).

Fixed: `stepFieldMessage` now requires a non-empty `student_id` for regular levels (same step-2 gate as university/faculty/department), so "Next" stays disabled — with an explicit "Please enter your student ID" message — until it's filled, and a restored draft missing it is clamped back to Academic Details instead of resuming past it. The label changed to "Student ID *" and the placeholder dropped "(optional)", matching the other required fields' styling. The submit mapping now sends `student_id` unconditionally for regular levels (safe — validation guarantees it's non-empty by the time submit is reachable), closing the silent-omission path entirely rather than just making the field harder to skip in the UI.

`organization_id` (UnderGrad/graduate) has the identical doc-says-required-form-treats-optional shape per the same table — **deliberately not changed**, see #51 above for why.

New regression test in `src/pages/Onboarding.test.tsx` ("student ID is required for regular levels") — confirmed to fail against the pre-fix code (Next stayed enabled, no blocking message) and pass against the fix; also confirmed the fix correctly clamps a restored step-3 draft missing `student_id` back to step 2, which required updating one pre-existing test's seed data. Not live-verified against the real backend end-to-end (would need a pending/not-yet-onboarded test account's OTP to reach this screen, which this session didn't have) — verified instead by matching the exact documented contract and a passing/failing regression test pinning the before/after behavior.

`type-check`/`lint`/`build` all pass; full suite **168/168 tests**.

### Course certificates (2026-11-11)

53. **Enrolled-list pagination is documented incompletely.** `docs/STUDENT_API_PAYLOADS.md` §13 shows only `current_page`, `data`, `per_page`, `total` and doesn't list a `page`/`per_page` query parameter. The certificate collection sends `?page=N` (Laravel's standard) and decodes whichever pagination hints come back, but this was only exercised against a fake API and unit tests — **confirm with the backend owner** that `page` is honoured and what the real paginator keys are. If the API ignores `page`, the collection stops after one page (repeat detection) and older completions are not reachable.
54. **`GET .../progress` wrapper is ambiguous in the docs.** §15 says "same `CourseProgressResource` shape as §13" (unwrapped), while the existing client adapter (`getCourseProgress`) reads `data.progress`. The certificate decoder accepts both; the real response was not inspected (no backend available this session). The nested `course.title` is required by the certificate and is documented, but unverified live.
55. **The guide's contract is partly stale.** It cites "STUDENT_API_PAYLOADS(2)" §§8/13/15/17; the in-repo `STUDENT_API_PAYLOADS.md` agrees on §8 (`data.student.full_name`) and §13 (nested paginator) but §17's POST example carries no `is_completed`/nested course, as the guide itself notes — so the POST response is never used for eligibility.
56. **Pre-existing: percentage-based "Completed" on the dashboard / My courses.** `EnrolledCourses.tsx` buckets by `progress_percent >= 100` and, like `Dashboard.tsx`, reads only page 1 of `/courses/enrolled`. Not changed (out of scope, existing behaviour); the certificate collection does not use it.
57. **Image decoding in background tabs.** `Image.decode()` can stall in a hidden tab; certificate rendering now waits on the `load` event instead. Seen while verifying (a hidden Browser pane made renders fall back to plain art after an 8 s timeout, before the fix). Rendering a certificate in a backgrounded tab is still slower than in a visible one.
58. **Not verified on real devices:** native file sharing (`navigator.share` with files) on iOS Safari / Android Chrome / WhatsApp, how each browser handles the download of a PNG/PDF (some open it instead), Safari's `CompressionStream` (PDF falls back to JPEG where absent), and canvas rendering of the bundled fonts on low-end phones. Verified: the PNG/PDF bytes in desktop Chromium (the Claude Browser pane), the share *call* with a stubbed `navigator.share`, and the fallback path (this browser has no Web Share).
59. **Certificates are only regenerable from current data.** If a course is removed, a student unenrols or completion is reset, the preview becomes unavailable; downloaded files stay on the student's device. Previously downloaded files aren't re-validated. The copy says it's a celebration, not an accredited qualification.
60. **PDF text isn't searchable** (the page is one embedded image) — accepted for V1 in the guide.

### Formula block contrast in dark mode (2026-11-14)

61. **Fixed — formula text was nearly invisible in dark mode (~1.3:1).** The `formula` wrapper in `MiniLessonRenderer.tsx` set a background but no text colour. KaTeX draws glyphs, fraction rules and `\boxed` borders in `currentColor`, so it inherited the light-theme `:root` colour (`#213547`) on the dark block (`gray-800/60` over `gray-900`). Now `text-gray-900 dark:text-gray-100` (≈17:1 light, 14.4:1 dark). Error text (parse errors, undefined commands such as `\ce`, disabled `\href`) used a fixed `#cc0000` (2.7:1 on dark); it is now `errorColor: "var(--formula-error)"`, defined in `index.css` as `#cc0000` (light, unchanged) and red-300 (dark, 8.4:1). A Tailwind override of `.katex-error` would not have worked: undefined commands render as inline-styled spans, not `.katex-error`. Verified by mounting the real renderer in the running app in both themes and measuring computed colours; 3 tests in `MiniLessonRenderer.formula.test.tsx` fail on the old code. The CSS-variable values themselves are covered only by that browser check (Vitest blanks CSS files).
62. **Open — colours chosen by the author can't follow the theme.** A `\color`/`\textcolor` in a formula is one fixed colour on a block that is light in light mode and dark in dark mode. None of the 148 CSS colour names reaches 4.5:1 on both; 28 reach 3:1. `\textcolor{blue}` is 1.8:1 on dark, orange/yellow are under 2:1 on light, and `\colorbox` is unreadable in one theme whatever the colour. The renderer doesn't override author colours (that would change what the author wrote). Guidance and checker warnings: `docs/LATEX_FORMULA_GUIDE.md` rule 9 and `scripts/check-latex.mjs`. Existing lessons that already use such colours will still look poor in dark mode until edited.
